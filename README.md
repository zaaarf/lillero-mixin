# Lillero-mixin
Lillero-mixin is a Mixin plugin capable of applying [Lillero](https://github.com/zaaarf/lillero) ASM patches without
needing to inject itself as a JAR library. While slightly dirtier code-wise, this has the key advantage over the older
[Lillero-loader](https://github.com/zaaarf/lillero-loader) of being compatible with both Forge and Fabric - and, barring
major API changes, with any other future mod loader that will try to force Mixin on you.

## How to use
1. Get this as well as the [core](https://github.com/zaaarf/lillero) into your game classpath. The easiest way is to
	bundle them together with your mod.
2. Create a class extending `ftbsc.lll.mixin.LilleroMixinPlugin`. You may or may not want to customize behaviour by
	overriding the plugin's various methods.
3. Write an empty class or interface with a `@Mixin` annotation listing all the classes that will be modified.
	- If you are using the [processor](https://github.com/zaaarf/lillero-processor), this step is considerably simpler;
		just pass the `fakeMixin` compiler argument with the fully qualified name you wish the class to have.
4. Write an appropriate Mixin configuration, specifying the empty Mixin you generated or wrote, and the class you wrote
	during step 2 as plugin. A minimal example (for Fabric) is provided below:

```json
{
	"required": true,
	"package": "mymod.patches",
	"plugin": "mymod.mixin.MyLilleroMixinPlugin",
	"mixins": ["FakeMixin"]
}
```

All that's left to do at this point is to tell your mod loader to use that Mixin configuration file; if you are unsure
of how to do this, refer to your mod loader's docs.

### On the Mixin package
Due to constraints in the loading environment, Lillero-mixin needs a way to recognize your mod's injectors from those
generated by another mod. Bottom line is that all your classes implementing IInjector need to be in the same package,
which MUST correspond to the mixin package as defined in the json config (as explained above).

If you are using the [processor](https://github.com/zaaarf/lillero-processor), this implies that either all your `@Patch`
and `@BareInjector` classes are located in the same package. Alternatively, you can pass the `outputPackage` argument and
place all your `@BareInjector`s, if any, in that same place. Refer to the processor's docs for caveats on this approach.
